1. 先学会读 MLIR

IR 是 intermediate representation，中间表示。编译器不直接把 Python 变成机器码，而是先把程序写成一种它方便分析和改写的文本格式，改写很多遍，最后再输出机器码。MLIR 就是这样一种格式，它的特点是可以同时容纳许多不同抽象层次的“方言”。

片段叫什么含义
%4SSA 值这一行算出来的结果。每个 %名字 只被赋值一次，之后只读不写，所以编译器看一眼就知道数据从哪来、到哪去。名字本身只是编号，没有含义
=左边是结果，右边是运算
torch.aten.mm操作名（op）点号前是方言名 torch，点号后是这个方言里的操作 aten.mm。所有操作都是“方言.操作”的形式
%arg0, %3操作数输入。%arg0 是函数参数，%3 是前面某一行的结果

类型写在每一行里，是 MLIR 的一个重要习惯：编译器在任何一步都能立刻知道每个值的形状和数据类型，不需要回头去推。

1.2 带“身体”的操作：region 与 block

有些操作内部还包着一段代码。最常见的是后面会反复出现的 linalg.generic，下面是第 8 步里的真实片段：

片段含义
indexing_maps = [...]每个输入输出张量怎么随循环变量取元素。下一小节细讲
iterator_types = ["parallel", "parallel"]有两层循环，两层都是 parallel，也就是各个元素之间互不依赖，可以任意顺序甚至同时计算
ins(%4, %__hoisted_tensor_64xf32 …)两个输入：矩阵乘的结果、提前算好的偏置
outs(%2 …)一个输出：结果写进哪个张量
{ ^bb0(%in, %in_6, %out): … }花括号里是一个 region，region 里是 block，^bb0 是 block 的名字。block 的参数代表“当前这一个元素”
linalg.yield %16把这一个元素的计算结果交出去，写进输出的对应位置

block 的参数怎么和输入对上？按位置。规则是：block 的参数先依次对应 ins 里的每个操作数，再依次对应 outs 里的；indexing_maps 里的 map 也按同样的顺序排。三组列表竖着对齐读：

位置操作数它是什么indexing_mapblock 参数
第 1 个%4（ins）矩阵乘的结果，17×64(d0, d1) -> (d0, d1)%in
第 2 个%__hoisted_tensor_64xf32（ins）提前算好的偏置，64 个数(d0, d1) -> (d1)%in_6
第 3 个%2（outs）输出张量，17×64(d0, d1) -> (d0, d1)%out

循环走到第 d0 行、第 d1 列时：%in 是 %4[d0][d1]；%in_6 是偏置的第 d1 个，因为它的 map 只保留了 d1，同一列的 17 行都拿到同一个偏置，这就是广播；%out 对应输出的 [d0][d1]，linalg.yield 把结果写到这里。所以 body 第一行 arith.addf %in, %in_6 就是“这一格的矩阵乘结果加上这一列的偏置”。

d0、d1 是什么？是 linalg.generic 自带的隐形循环的下标，d 是 dimension 的意思。循环有几层，看 iterator_types 有几项，这里两项，所以是 d0、d1；矩阵乘有三项，就多一个 d2。每层走多少次，代码里没写，是编译器从 indexing_map 和张量形状反推的：输出的 map 是 (d0, d1) -> (d0, d1)、形状是 17×64，所以 d0 取 0–16（行号），d1 取 0–63（列号）；偏置的 map (d0, d1) -> (d1) 配上长度 64，也和 d1 的范围吻合。写成普通代码就是：

%out 是 %2 吗？%2 是整个输出张量，%out 是其中“当前这一格”的那个元素，类型是 f32。再往上看 %2 的来历：

%2 是 tensor.empty()，只声明“要一块 17×64 的张量”，里面没有有意义的值；gelu 的 body 也从头到尾没有读 %out。这里 outs 的作用只是告诉编译器结果的形状和去处，这种写法叫 destination-passing style。结果也不是把 %2 改掉了，而是产生一个新值 %5：在 tensor 这一层，值是不可变的。要到第 16 步缓冲化之后，这个“去处”才变成一块会被原地写入的真实内存。

对比同一段里的 linalg.matmul：它的 outs 是 %3，也就是先用 linalg.fill 把 %2 填成 0 的结果。矩阵乘是累加，每一步都在做 out = out + a × b，要读 out 的当前值，所以必须先清零。同样是 outs，在逐元素运算里只是“去处”，在累加运算里还是“初值”。

名字本身没有含义。%in、%in_6、%out 是打印 IR 时自动起的：来自 ins 的叫 in，来自 outs 的叫 out，重名时加一个编号后缀去重，_6 只是去重用的编号，和“第几个”无关。把它们改名成 %a、%b、%c，意思完全不变，决定对应关系的只有位置。

所以这段代码的意思是：对 17×64 的每个位置，取矩阵乘结果和偏置，做 body 里那 9 步标量运算，把结果写到输出的同一位置。整个 gelu 就是这 9 步：加偏置、立方、乘 0.044715、相加、乘 0.7979、tanh、加 1、乘 0.5x 的另一半、相乘。

1.3 affine_map：循环变量到数组下标的映射

看第 7 步里矩阵乘的写法：

affine_map<(d0, d1, d2) -> (d0, d2)> 可以读成一个小函数：给定三层循环的下标 d0、d1、d2，返回该取数组的哪个位置。三个 map 分别对应两个输入和一个输出：

map对应读法
(d0, d1, d2) -> (d0, d2)输入 x，17×32x[i][k]，i 是行，k 是被求和的那一维
(d0, d1, d2) -> (d1, d2)输入权重，64×32W[j][k]。注意是 W 本身而不是它的转置
(d0, d1, d2) -> (d0, d1)输出，17×64y[i][j]

合起来就是 y[i][j] += x[i][k] × W[j][k]，正是 x 乘以 W 的转置。编译器后面所有的分块、向量化，都是在改写这三层循环。

1.4 其他会见到的结构

  • module：最外层的容器，一个文件就是一个 module。
  • func.func / util.func：函数。util.func 是 IREE 自己的函数写法，功能相同。
  • attribute：花括号里的 {stream.affinity = …} 这类键值对，是贴在操作上的附加信息，不参与计算，但会影响编译器怎么处理它。
  • #map = …：文件开头的别名定义，后面用 #map 代替很长的 affine_map，纯粹为了少写字。

2. pass 与 lowering 是什么

方言是一组操作的集合，每个方言工作在一个抽象层次上。torch 方言说的是 PyTorch 的语言，linalg 说的是循环和张量，vector 说的是向量寄存器，llvm 已经接近机器指令。

pass 是编译器里的一道工序：读入一份 IR，做一件具体的改动，交出一份仍然合法的 IR。下面是一个真实的例子，iree-global-opt-propagate-linalg-transpose 这个 pass 执行前后，矩阵乘那一行的变化：

执行前，矩阵乘读的是一个已经转置好的 32×64 权重，这个转置需要单独算一遍。执行后，矩阵乘直接读原始的 64×32 权重，把“转置”写进了 indexing_maps 里的 (d1, d2)。转置这个操作就此消失，这就是一个 pass 做的全部事情。

lowering，降级，就是一长串这样的 pass 依次执行，每道只把 IR 往下推一小步，最终从 PyTorch 的语义一路推到机器指令。整体路线见图 1。

pass 大致分三类：

  • 转换类：把一种方言换成另一种，例如 StableHLO 换成 linalg、linalg 换成 vector。这是字面意义上的降级。
  • 变换类：方言不变，只改结构，例如融合、分块、缓冲化。
  • 分析与标注类：不改计算，只贴属性，例如决定每个运算放在哪个设备。

另有两个清理工几乎夹在每道工序之间：canonicalize 负责化简，比如把乘 1 去掉；cse 负责合并重复的计算。一次编译里它们会被调用几百次。

pass 还有一个“作用对象”：有的作用于整个 module，有的只作用于一个函数，有的只作用于一个内核。编译器的 pass 管理器按层级把它们套起来运行，所以代码生成阶段的 pass 会对每个内核各跑一遍。

第一部分 · 前端：从 PyTorch 到 StableHLO

步骤 1 · PyTorch 模型

输入：Python 代码  →  输出：nn.Module  ·  负责的 pass：—

起点就是第 0 节那段 Python 代码。PyTorch 执行时是“边跑边算”的：每行 Python 立刻调用一个算子。这对训练很方便，但编译器拿不到“整个程序长什么样”，没法做全局优化，所以第一件事是把它变成一张静态的图。

步骤 2 · torch.export：把 Python 变成计算图

输入：nn.Module + 示例输入  →  输出：FX 图（ExportedProgram）  ·  负责的 pass：torch.export.export()

用一个示例输入把 forward 跑一遍，记录下每次调用了哪个底层算子，得到 FX 图。这一步之后，Python 的 if、for、类、方法调用都消失了，只剩一串算子调用。

看点
  • self.fc(x) 变成了一个 aten.linear 节点，权重和偏置变成了函数参数 p_fc_weight、p_fc_bias。
  • gelu 公式被逐项拆开，每个 + − × 都是一个节点，常数 0.7978845608028654 就是 √(2/π)。
  • 每个节点末尾的 x = … = None 是在释放不再用的变量，可以忽略。

步骤 3 · 导入为 Torch 方言

输入：FX 图  →  输出：Torch 方言 MLIR  ·  负责的 pass：fx.export_and_import(…, output_type="torch")

torch-mlir 把 FX 图逐个节点翻译成 MLIR。这是第一次出现 MLIR 格式，操作名、类型都还是 PyTorch 的样子。

看点
  • aten.linear 被拆成三件事：aten.permute 转置权重、aten.mm 矩阵乘、aten.add.Tensor 加偏置。
  • 两处 aten.mul.Scalar … %int1 是乘 1。这是分解 linear 时留下的系数，本身没有意义，后面会被消掉或提前算好。
  • 权重不再是参数，而是 torch.vtensor.literal(dense_resource<…>)：常量本体放在文件末尾的 dialect_resources 里，正文只放一个引用名，这样正文不会被几千个数字淹没。

步骤 4 · 降级为 StableHLO

输入：Torch 方言  →  输出：StableHLO MLIR  ·  负责的 pass：fx.export_and_import(…, output_type="stablehlo")

StableHLO 是一个与框架无关的“交接格式”，JAX、TensorFlow、PyTorch 都能导出它。Coral NPU 的编译器只认 StableHLO 和 TOSA 两种输入，所以必须降到这里。

看点
  • 类型从 !torch.vtensor<[17,32],f32> 变成标准的 tensor<17x32xf32>。从这一行开始，已经看不出模型来自 PyTorch。
  • aten.permute → stablehlo.transpose，aten.mm → stablehlo.dot_general，contracting_dims = [1] x [0] 说明对第一个输入的第 1 维和第二个输入的第 0 维求和。
  • 为什么多出一大堆 convert / reshape / broadcast_in_dim？因为 PyTorch 里的标量常数，比如 0.5，在这里被表示成 1 个元素的 64 位浮点张量，要先转成 32 位、去掉维度、再广播成 17×64，才能和张量逐元素相乘。这些看起来很啰嗦，但后面的 pass 会把它们全部化简掉。

第二部分 · 编译器前段：整理与优化整个模型

步骤 5 · 输入转换：StableHLO → linalg

输入：StableHLO  →  输出：linalg + tensor + arith + math  ·  负责的 pass：iree-stablehlo-to-iree-input

编译器的第一件事是把 StableHLO 换成它内部通用的表示：linalg 描述计算的循环结构，tensor 负责张量的分配和变形，arith 与 math 负责标量运算。之后所有优化都在这套表示上进行。

看点
  • 整个模型现在是 28 个 linalg 操作。每个 StableHLO 操作都变成了“先 tensor.empty 分配一块输出，再用一个 linalg 操作填它”的固定套路。
  • stablehlo.transpose 变成了一个 linalg.generic，它的 body 只有 linalg.yield %in：原样搬运，搬运的方式由 indexing_maps 里的 (d1, d0) 决定，这就是转置。
  • dot_general 变成了 linalg.fill 清零加 linalg.matmul。矩阵乘是累加运算，输出必须先清零。
  • 每个 stablehlo.multiply 都变成一个 body 里只有一条 arith.mulf 的 generic。“对每个元素做一次乘法”这件事，被拆成了“循环结构”和“单个元素上的运算”两部分。

步骤 6 · 确定设备与函数接口，并分配设备

输入：linalg  →  输出：带设备标签的 linalg  ·  负责的 pass：iree-abi-wrap-entry-points、iree-hal-materialize-target-devices、coralnpu-affinity-annotation

编译器要知道有哪些设备、函数怎么被外部调用、每个运算放在哪个设备上。这一步由几个 pass 组成：把入口函数包装成接收 !hal.buffer_view 的形式，从命令行参数生成两个设备，再由 Coral NPU 自己的 pass 给每个 linalg 操作贴上设备标签。

看点
  • @__device_0 是主机（local，x86），@__device_1 是 NPU（coralnpu，embedded-elf-riscv_32）。
  • 矩阵乘标给了 @__device_1，清零和逐元素运算标给了 @__device_0。原因是 NPU 的规则是一张白名单：矩阵乘在里面，linalg.generic 和 linalg.fill 不在里面。
  • 但这只是初步标签。到第 9 步你会看到，逐元素运算最终会跟着矩阵乘一起去 NPU。
  • 入口函数现在接收 !hal.buffer_view，也就是运行时传进来的一块带形状信息的内存。外部调用者不认识 MLIR 的 tensor 类型，这里是 MLIR 世界和外部世界的接口。

步骤 7 · 全局优化：吸收转置、提前算好常量

输入：带设备标签的 linalg  →  输出：更少的 linalg + 预先算好的全局常量  ·  负责的 pass：iree-global-opt-propagate-linalg-transpose、iree-util-hoist-into-globals、iree-consteval-jit-globals

步骤 8 · 融合：把一串逐元素运算合成一个

输入：25 个 linalg 操作  →  输出：3 个 linalg 操作  ·  负责的 pass：iree-dispatch-creation-elementwise-op-fusion

现在从矩阵乘到输出之间还有二十多个逐元素的 generic，每个都要完整地读一遍 17×64 的张量、写一遍 17×64 的张量。融合把它们合并成一个 generic，body 里依次做完所有标量运算，中间结果不再落到内存里。

看点
  • 只剩 3 个 linalg 操作：清零、矩阵乘、一个融合后的 generic。
  • generic 的第二个输入是 %__hoisted_tensor_64xf32，就是第 7 步算好的偏置。它的 indexing_map 是 (d0, d1) -> (d1)：只看列号，同一列的每一行都用同一个偏置，这就是“广播”。
  • 第 4 步那些 convert、reshape、broadcast 全部消失了，乘 1 也被化简掉了：body 第一行直接是 arith.addf，矩阵乘结果加偏置。
  • hal.tensor.import 和 hal.tensor.export 分别把外部传入的 buffer_view 转成 tensor、再把结果转回去。

第三部分 · 切分内核与调度

步骤 9 · 形成 dispatch：决定哪些运算打包成一个内核

输入：融合后的 linalg  →  输出：flow.executable + flow.dispatch 调用  ·  负责的 pass：iree-dispatch-creation-form-dispatch-regions、clone-producers-into-dispatch-regions、iree-flow-outline-dispatch-regions

内核就是一段可以被独立下发到某个设备执行的代码。编译器先用 flow.dispatch.region 圈出哪些操作属于同一个内核，再把圈出来的部分剪成独立的函数。

接着清零操作被复制进区域里，再把整个区域剪出去，成为一个独立的 flow.executable。主函数里只剩一次调用：

看点
  • 整个区域被标为 @__device_1，也就是 NPU。区域里的 generic 自己的标签是主机，但它被融合进了矩阵乘的区域，于是跟着一起上了 NPU。设备的最终归属由标签、融合、相邻关系共同决定。
  • 内核的参数类型变成了 !iree_tensor_ext.dispatch.tensor<readonly:…> 和 <writeonly:…>。内核只能通过这四个参数读写外部数据，读写方向是明确声明的。
  • 内核里第一件事是 dispatch.tensor.load 把参数读成普通 tensor，最后一件事是 dispatch.tensor.store 写回。中间就是第 8 步那三个操作。
  • 如果模型更大，这里会出现很多个 flow.executable。toy ViT 就有 23 个。

步骤 10 · stream：安排内存和执行顺序

输入：flow  →  输出：stream  ·  负责的 pass：iree-stream-conversion 及其后一系列 iree-stream-* pass

tensor 是抽象的“值”，没有说它放在哪块内存、什么时候算。stream 这一层把它们落实成带大小的内存资源，并安排异步执行的先后顺序。

看点
  • 内存大小都已经算好：输入 2176 = 17×32×4 字节，权重 8192 = 64×32×4，偏置 256 = 64×4，输出 4352 = 17×64×4。
  • 资源分两种：resource<external> 是外部传进来或要交出去的输入输出，resource<constant> 是常量。
  • stream.cmd.execute on(@__device_1) 表示在 NPU 上执行一批命令，这里只有一条 stream.cmd.dispatch。每个缓冲前的 ro 和 wo 是只读和只写。
  • timepoint 是时间点，代表“某件异步的事完成了”。await 就是等它完成。执行是异步的，主机下发命令后不会停下来等，除非明确要求。

步骤 11 · hal：确定内核看到的内存接口

输入：stream  →  输出：hal.executable + 绑定  ·  负责的 pass：iree-hal-materialize-interfaces

hal 是硬件抽象层。这一步把 stream 里的资源映射成内核可以访问的“绑定”，并把内核放进一个带目标平台信息的 hal.executable 里。

看点
  • 内核变成了没有参数的函数，数据通过 hal.interface.binding.subspan 从绑定里取。
  • 偏置和权重共用 binding(1)：偏置在偏移 0，权重在偏移 256。编译器把所有常量打包成一块，减少绑定的数量。
  • hal.executable.variant @embedded_elf_riscv_32 说明这是给 RISC-V 目标的版本。如果一个内核同时要在主机上跑，还会有一个 x86 的 variant。

第四部分 · 代码生成：把一个内核变成 NPU 指令

从这里开始，只关注这一个内核。前面的 linalg 描述的是“算什么”，接下来要决定“怎么算”：循环怎么切、怎么用上向量寄存器、数据放在哪。

步骤 12 · 选择分块参数

输入：hal.executable  →  输出：带 lowering_config 的 linalg  ·  负责的 pass：coralnpu-tile-size-selection-register、-dtcm、-workgroup、iree-hal-configure-executables

Coral NPU 的编译器用三个 pass，依次按向量寄存器、片上内存 DTCM、工作组三个层次，给矩阵乘贴上分块参数，然后选定代码生成的流水线。

pass 执行后matmul 上的 lowering_config
…-registervector_common_parallel = [8, 8, 0], vector_reduction = [0, 0, 1]
…-dtcmcache_parallel = [16, 0, 0], cache_reduction = [0, 0, 0], vector_common_parallel = [8, 8, 0], vector_reduction = [0, 0, 1]
…-workgroupcache_parallel = [16, 0, 0], cache_reduction = [0, 0, 0], distribution = [16, 0, 0], vector_common_parallel = [8, 8, 0], vector_reduction = [0, 0, 1]

每个方括号里的三个数，对应矩阵乘的三层循环：第 0 维是输出的行，第 1 维是输出的列，第 2 维是求和的 k。0 表示这一维不切。

参数值含义
vector_common_parallel[8, 8, 0]最内层每次算一个 8 行 × 8 列的小块。NPU 的向量寄存器是 128 位，编译目标里 native_vector_size 是 32 字节，一次能装 8 个 f32
vector_reduction[0, 0, 1]求和维每次走 1 步：每一步用 A 的一列乘 B 的一行，加到 8×8 的累加器上
cache_parallel[16, 0, 0]按片上内存容量再切一层：每次处理 16 行
distribution[16, 0, 0]工作组的划分：每 16 行分给一个工作组。17 行因此分成两个工作组

同时选定的流水线是 CPUDoubleTilingExpert，意思是按“先切大块、再切到向量大小”的两级分块方式生成代码。这是 IREE CPU 后端的现成流水线，Coral NPU 借用了它，只换了分块参数。

步骤 13 · 按工作组切分

输入：带配置的 linalg  →  输出：scf.forall 循环  ·  负责的 pass：iree-codegen-tile-and-distribute-to-workgroups-using-forall-op

把输出的行按 16 行一组分开，每组是一个可以独立执行的工作组。

看点
  • scf.forall (%arg0) = (0) to (17) step (16)：%arg0 取 0 和 16，一共两个工作组。forall 表示各次迭代可以并行。
  • affine.min (-d0 + 17, 16) 算出这一组实际有几行：第一组 16 行，第二组 17 − 16 = 1 行。于是张量类型里出现了问号 tensor<?x64xf32>，行数不再固定。
  • tensor.extract_slice 从大张量里切出这一组要用的部分，tensor.parallel_insert_slice 把算好的部分放回去。原来的三个操作被原样搬进了循环体里。

步骤 14 · 继续切到向量大小

输入：scf.forall  →  输出：五层循环  ·  负责的 pass：iree-llvmcpu-tile-and-fuse-producer-consumer（执行 3 次）、iree-codegen-forall-to-for

在每个工作组内部，再按 16 行、8 行、8 列切下去，最内层对求和维 k 逐个循环，形成一个多层循环嵌套。

看点
  • 从外到内五层：工作组（每 16 行）、缓存块（每 16 行）、行块（每 8 行）、列块（每 8 列）、求和（k 从 0 到 31，每次 1）。
  • 最内层的矩阵乘现在只处理 tensor<?x1xf32> 乘 tensor<8x1xf32>：A 的一小列乘 B 的一小行，加到 8×8 的块上。
  • gelu 那个 generic 没有进入 k 循环，而是紧跟在它后面，对算完的 8×8 块做一次。这叫“融合到消费者”：每个块算完立刻做激活，不必等整个矩阵乘结束。
  • 为什么行块是 8，缓存块也是 16？因为这个例子太小，一共才 17 行，两层 16 的切分都只切出一块。模型更大时这几层才会拉开差距。

步骤 15 · 向量化

输入：scf 循环里的 linalg  →  输出：vector 方言  ·  负责的 pass：iree-codegen-generic-vectorization

把最内层的小块运算换成向量操作。从这里开始，一次操作处理的不再是一个数，而是一整排 8 个数。

看点
  • vector.transfer_read 把一块内存读进一个向量值，比如 vector<8x8xf32>；vector.transfer_write 写回去。
  • vector.contract 是向量化后的矩阵乘，它的 indexing_maps 和第 1.3 节里的一模一样，只是操作对象从张量变成了 8×8 的向量。
  • vector.create_mask 生成掩码。最后一组只有 1 行，读写时只处理掩码为真的那一行，其余 7 行不碰，这就是图 3 里黄色那一行的处理方式。
  • gelu 的 9 步运算原封不动地变成了对 vector<8x8xf32> 的运算，比如 math.tanh %28 : vector<8x8xf32>。

步骤 16 · 缓冲化：张量变成内存

输入：vector + tensor  →  输出：vector + memref  ·  负责的 pass：iree-codegen-iree-comprehensive-bufferize

到目前为止，tensor 都是“值”：每次修改都在概念上产生一个新张量，没有说数据存在哪。缓冲化把 tensor 换成 memref，也就是一块具体的内存，修改就是原地写入。

看点
  • 出现了三块 memref.alloca() : memref<8x8xf32>：在栈上开的 8×8 临时空间，用来放累加器等中间结果。
  • memref.subview 是在已有内存上开一个“窗口”，只是换个视角看同一块内存，不复制数据。它取代了之前的 tensor.extract_slice。
  • 类型里的 strided<[64, 1], offset: ?> 描述内存布局：行与行相隔 64 个元素，同一行相邻元素相隔 1 个。
  • 循环不再需要把张量作为结果传出来，因为数据是原地写进输出缓冲的。

步骤 17 · 把向量运算拆成硬件能执行的形状

输入：二维 vector  →  输出：一维 vector.fma  ·  负责的 pass：iree-llvmcpu-virtual-vector-lowering、iree-codegen-vector-transfer-lowering

硬件的向量寄存器只能装一维的一排数，没有 8×8 这种二维向量。这一步把二维的 vector.contract 拆成 8 条一维的 vector.fma，每条处理累加器的一行。

看点
  • 每一步 k：先读出 A 的一列 8 个数 %27、B 的一行 8 个数 %31。
  • 然后对累加器的第 0 行：取出 A 列的第 0 个数，vector.broadcast 复制成 8 份，做 vector.fma %33, %31, %34，即 累加器第 0 行 += A[0] × B 行。第 1 行用 A[1]，依此类推，一共 8 条 fma。
  • fma 是 fused multiply-add，融合乘加：一条指令同时完成 a×b+c，比分开做乘和加更快也更精确。
  • arith.select 配合掩码：对超出范围的行保留原值，不写入新结果。

步骤 18 · 展开数学函数

输入：含 math.tanh 1 处、math.powf 1 处  →  输出：含 math.tanh 0 处、math.powf 0 处  ·  负责的 pass：iree-codegen-math-transform

硬件没有 tanh 这样的指令，也没有通用的幂运算指令。这一步用加减乘除把它们重新写出来。

看点
  • math.powf(x, 3) 变成了两次乘法：%68 = x*x，%69 = %68*x。编译器看出指数是常数 3，就不必调用通用的幂函数。
  • math.tanh 变成了一个有理多项式近似：先把输入夹在一个范围内（cmpf / select），再算一个分子多项式和一个分母多项式（那一串 math.fma），最后相除。对很小的输入，直接返回输入本身。
  • 每一步都作用在 vector<8x8xf32> 上，所以 64 个 tanh 是一起算的。

步骤 19 · 降到 llvm 方言

输入：vector + memref + scf  →  输出：llvm 方言  ·  负责的 pass：convert-scf-to-cf、iree-convert-to-llvm

把剩下的结构全部换成接近 LLVM 的形式：scf.for 这种结构化循环变成基本块加跳转，memref 变成指针和地址计算，vector 与 arith 变成 llvm 的指令。这是 MLIR 这一侧的最后一步。

看点
  • llvm 方言里共有 72 条 llvm.intr.fma，操作的都是 vector<8xf32>。
  • 函数参数变成了 !llvm.ptr，即指针。IREE 按约定把绑定、工作组编号等信息通过这几个指针传进内核。
  • 同一个内核，第 13 步时 46 行，到这里是 939 行：抽象被一层层兑现成了具体的指令。

步骤 20 · LLVM 生成 RISC-V 机器码

输入：LLVM IR  →  输出：RISC-V ELF  ·  负责的 pass：LLVM 后端（不是 MLIR pass）

MLIR 把 llvm 方言翻译成标准的 LLVM IR 文件，交给 LLVM 后端。LLVM 负责最后的指令选择、寄存器分配和指令调度，输出 RISC-V 汇编，再汇编链接成 ELF。

统计（只算内核函数本身）条数
全部指令1,380（整个 .s 文件 2,303，其余属于链接进来的运行时辅助函数）
vfmadd.vv：向量 × 向量 + 向量57
vfmadd.vf：向量 × 标量 + 向量22
全部向量指令502
标量浮点指令16
vl2r.v / vs2r.v：成组读回 / 存出向量寄存器51 / 40
看点
  • 第 17 步的 vector.fma 最终变成了 vfmadd。其中一部分是 .vf 形式：LLVM 发现 fma 的一个输入是由标量广播来的，就直接用“向量乘标量”的指令，省掉了广播。
  • 一个 8 个 f32 的向量是 256 位，而 NPU 的向量寄存器是 128 位，所以每个向量占两个寄存器。这就是指令里 m2、vl2r 这类“2”的来源。
  • 51 条 vl2r.v 和 40 条 vs2r.v 是在把向量寄存器存到栈上又读回来，大量的 csrr vlenb 是在计算栈上的地址。原因是寄存器不够用：RISC-V 向量扩展有 32 个向量寄存器，两个一组就只剩 16 组，而 8×8 的累加器一个就要占 8 组，再加上 A 列、B 行和各种临时值，只好借用内存周转。这叫寄存器溢出，是这个内核一个明显的性能改进点。

步骤 21 · 主机侧程序：从 hal 到 vm

输入：stream + hal  →  输出：vm 方言 → model.vmfb  ·  负责的 pass：iree-hal-conversion、iree-vm-conversion 等

内核编好之后，主机侧的调度逻辑，也就是分配内存、提交内核、等待完成，被翻译成 IREE 虚拟机的字节码，和内核 ELF 一起打包进 vmfb。

看点
  • 每次推理，主机上的 main 只做五件事：检查输入形状是 17×32、在 NPU 上申请 4352 字节的输出、提交命令、等待完成、把输出包装成 17×64 的 buffer_view 返回。
  • 提交的命令缓冲 @__main_memoize_result_0_device_1 是在初始化时就录制好的，里面就是那一次 dispatch。因为形状固定，每次推理的命令都一样，录一次反复用。
  • 这里没有任何矩阵乘或加法。主机只负责指挥，计算全部在 NPU 的内核里。

步骤 22 · 在 NPU 仿真器上运行

输入：model.vmfb + 输入  →  输出：17×64 输出  ·  负责的 pass：运行时，不属于编译

运行时加载 vmfb：IREE 虚拟机在主机上执行第 21 步的 main；HAL 驱动把 RISC-V ELF 和三块缓冲交给 MPACT 仿真器，仿真器逐条执行第 20 步的指令，结果写回输出缓冲。

和 PyTorch 在 Mac 上算出的结果相比，1,088 个输出值的最大误差是 2.4e-07。误差来自浮点运算顺序不同，以及 tanh 用多项式近似，属于正常范围。

6. 术语表

IR
中间表示。编译器内部用来表示程序的格式。
MLIR
一种可以容纳多种抽象层次的 IR 框架，本身是 LLVM 项目的一部分。
方言 dialect
一组相关操作和类型的集合，比如 linalg、vector、llvm。
操作 op
IR 里的一条语句，形如 方言.名字。
SSA
静态单赋值。每个值只被赋值一次，便于分析数据流。
region / block
操作内部包含的代码块。block 可以有参数，以 ^bb 命名。
attribute
贴在操作上的附加信息，不参与计算。
affine_map
从循环下标到数组下标的线性映射。
pass
一道把 IR 改写成另一份 IR 的工序。
lowering 降级
把 IR 从高抽象层次改写到低抽象层次的过程。
canonicalize / cse
化简 / 公共子表达式消除，两种最常用的清理 pass。
tensor
张量值。不可变，没有内存位置的概念。
memref
内存引用。一块有地址、有布局的真实内存。
缓冲化 bufferization
把 tensor 换成 memref 的过程。
融合 fusion
把相邻的运算合并，中间结果不写回内存。
分块 tiling
把一个大循环切成多层小循环，让数据能装进寄存器或缓存。
向量化 vectorization
把逐个元素的运算换成一次处理一排元素的向量运算。
掩码 mask
指明向量里哪些位置有效，用来处理凑不满一整排的边界。
dispatch / 内核
一段可以被独立下发到某个设备执行的代码。
工作组 workgroup
内核执行时的并行单位，每个处理输出的一部分。
fma
融合乘加，一条指令完成 a×b+c。
寄存器溢出 spill
寄存器不够用时，把值临时存到内存再读回。
HAL
硬件抽象层。IREE 用它统一描述不同设备。
vmfb
IREE 的模块文件，内含调度字节码、内核二进制和常量。
