4. 逐步记录

4.1 模型定义与参考输出

结构：图像 32×32×3，patch 8×8 → 16 个 token，加 1 个 cls token 共 17 个；维度 32，2 个注意力头（每头 16 维），MLP 隐层 64，2 个 block，10 类输出。layernorm 与 gelu 手写成基础运算（mean、sub、pow、sqrt、div、tanh），目的是让图里只有 torch-mlir 支持较稳的算子。

导出脚本先用固定种子造输入，在 PyTorch 里跑一次前向，保存输入和 logits 作为后续比对的唯一标准。

4.2 torch.export：动态图 → FX 图

用示例输入把 forward 追踪一遍，得到 111 个 call_function 节点、17 种 ATen 算子：add.Tensor, cat, div.Tensor, expand, linear, matmul, mean.dim, mul.Tensor, permute, pow.Tensor_Scalar, reshape, select.int, softmax.int, sqrt, sub.Tensor, tanh, transpose.int。Python 层的结构在这一步消失：block 循环被展开，nn.Linear 变成 aten.linear 节点，参数变成图的输入（如 p_blocks_0_qkv_weight）。

4.3 导入为 Torch 方言 MLIR

torch-mlir 把 FX 节点逐个翻译成 MLIR。把 output_type="torch" 传给 export_and_import 可以停在这一层。这一层保留 PyTorch 的类型系统（!torch.vtensor、!torch.list<int>），共 190 个 torch.aten.* 算子。aten.linear 在这里已被分解为 permute + view + mm。

4.7 融合与 dispatch 切分

这一步解决的是粒度问题，与有几个设备无关：如果每条 linalg 操作都单独下发，准备参数、搬数据、启动执行的开销会远大于计算本身。融合还省掉中间结果的落盘，例如矩阵乘的输出直接在同一内核里接着算 gelu。

617 条操作被融合分组为 23 个不同的 dispatch 单元，主函数变成 33 次 flow.dispatch 调用（两个 block 形状相同，8 个单元被复用）。10 块权重提升为全局常量（@__constant_tensor_96x32xf32_3 等）。设备归属此时已作为属性挂在调用上：

几处从表里能直接读出来的事：

  • 融合的形态。矩阵乘单元大多带着紧随其后的逐元素运算：1 带偏置，10 带残差，14 带偏置和残差，13 带偏置和整个 gelu。7 把除以 √16 并了进去，9 把转置并了进去。
  • 为什么同形状的 LN 后半有四份（4、12、16、24）。逐行比对它们的函数体，只差两行：内嵌的 γ、β 常量指向不同的权重块（torch_tensor_32_torch.float32_1/_2 对 _3/_4 等）。权重被当作常量嵌进了单元内部，内容不同就无法合并。LN 前半（3）不含权重，所以一份被调用了 4 次。
  • 编译器把“只取 cls”提前了。模型最后只用 cls 那一行。block 2 的 fc2（26）因此只做矩阵乘，偏置和残差挪到了 27，而 27 只读两个 1×17×32 张量的第一行（sizes = [1, 1, 32]），其余 16 行的偏置和残差根本没算。末层 LN 也就只作用在 32 个数上，被拆成了 28–31 四个很小的单元。
  • softmax 此时还是一个整体算子 linalg.softmax，要到代码生成阶段才展开成 exp、求和、相除。

一个完整单元的原文，fc1 + gelu（dispatch_13）。linalg.generic 的函数体就是手写 gelu 的逐步计算：加偏置、立方、乘 0.044715、相加、乘 √(2/π) ≈ 0.7979、tanh、加 1、乘 0.5x。

融合的一个实例：dispatch_13 内同时含 linalg.matmul、math.tanh、math.powf，即 fc1 与紧随的 gelu 在同一个内核里。

4.8 调度：落实设备归属

先澄清三件容易混在一起的事。标注决定每个算子归哪个设备，它发生得最早：在全局优化阶段，由 NPU 插件的 pass 给 linalg 算子挂上 stream.affinity 属性（规则见第 6 节）。切分（4.7）决定粒度，把相邻操作融合成可独立编译、独立下发的函数；融合受设备属性约束，dispatch 也继承其中算子的属性，所以 flow.mlir 里每次调用上已经带着设备。调度是本步：依据这些属性，决定在哪个设备上分配缓冲、哪里需要跨设备传递、哪些相邻的同设备 dispatch 合并成一次提交。

stream.mlir 里 82 处标注 @__device_0、56 处标注 @__device_1；33 个 stream.cmd.dispatch 被组织进 13 个 stream.cmd.execute 区域（相邻且同设备的 dispatch 合并提交），另有 3 次 stream.cmd.copy、3 次 stream.timepoint.await、21 次资源分配。两个设备互相声明 unified_memory = true, transparent_access = true。

profile 之后编译器还给了一条 warning：多设备模块暂不支持 executable benchmarks。不影响产物。

4.10 运行与比对

run_vit.py 创建 local-sync 与 coralnpu 两个 HAL 设备（可用驱动列表为 ['local-sync', 'local-task', 'coralnpu']），用两者建 HAL 模块，mmap 加载 vmfb，上下文中的模块为 ['hal', 'module']，调用 module.main。IREE 虚拟机在主机上解释调度字节码：主机的 dispatch 直接调 x86 函数，NPU 的 dispatch 由 HAL 驱动交给 MPACT 仿真器执行对应的 RV32 ELF。LD_LIBRARY_PATH 指向 runtime/sim 是为了让驱动找到仿真后端的动态库。

6. 设备分配规则：主机上的 15 次是 fallback

哪个算子去 NPU、哪个留主机，由编译器里的 compiler/Transforms/CoralNPUAffinityAnnotation.cpp 决定。它在全局优化阶段逐个检查算子，给它们挂上 stream.affinity 属性；规则是一张算子类型白名单，不在白名单里的被明确标给主机，源码注释称之为 host device fallback。

为什么 layernorm 和逐元素运算都落到了主机。白名单里其实有 linalg.reduce 和具名的 linalg.add / sub / mul / div / sqrt，但 StableHLO 输入转换产生的不是这些具名形式，而是通用的 linalg.generic（归约、逐元素、转置都是）。linalg.generic 不在白名单里，于是全部走了 fallback 分支。这是形式对不上白名单，不是 NPU 做不了这些运算。

两个没进白名单却在 NPU 上执行的单元。linalg.softmax 在标注阶段没有被处理，它前后紧挨着两个标给 NPU 的批量矩阵乘，后续的设备分析把它放到了 NPU（dispatch_8）。dispatch_6 的 17×6×16 转置在标注阶段还不存在（global-optimization.mlir 中搜不到这个形状），是切分 dispatch 时才生成的，同样随相邻算子去了 NPU。反过来，fc1 后面的 gelu 是被标给主机的 linalg.generic，却与矩阵乘融合进了同一个 NPU 内核（dispatch_13）。最终归属 = 标注 + 融合 + 相邻关系，三者共同决定。

代价。每次 fallback 都是一次设备切换。一个 Block 内 LN 出现两次，执行流在 NPU 与主机之间往返四趟；stream.mlir 里 33 次 dispatch 被分成 13 个提交区域，就是这些切换的直接体现。

10. 未验证事项与局限

  • 指令集出入。coralnpu 硬件仓库 README 写的是 rv32imf_zve32x（整数向量），而编译器以 +zve32f（浮点向量）为目标，MPACT 也正确执行了这些指令。真实 RTL 是否支持浮点向量指令未验证，需要把这些 ELF 放到 Verilator 周期精确仿真上确认。
  • 没有性能数据。MPACT 是指令级功能仿真；这条路线的运行器目前只给墙钟时间，不输出 NPU 指令数或周期数。0.158 秒不能当作 NPU 性能。
  • 主机侧 15 次 dispatch 是白名单外的 fallback（第 6 节）。layernorm 与逐元素运算以 linalg.generic 形式出现而未被放到 NPU，由此带来的设备往返开销在功能仿真里看不出来。
  • 工作量占比是静态估算。80.9% 来自编译器按张量元素数的估计，不反映每次 NPU dispatch 的装载与数据搬运开销。
  • f32、未量化。整条链路是浮点模型。int8 量化模型经 torch-mlir 能否保留量化语义到 StableHLO 未尝试。
  • 运行在 Rosetta 翻译的 x86 容器里。功能结果不受影响，编译与仿真耗时不代表原生 x86 主机。
  • pip 取包失败的根因没有查清（第 8 节第 7 条），只是换源后绕过。
  • 权重随机。验证的是数值一致性，不是分类精度。
